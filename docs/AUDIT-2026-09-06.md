### P0-2 API Key 鉴权中间件被完全绕过

`netease163/api/app.py:151`

```python
skip_paths = ("/docs", "/openapi.json", "/redoc", "/", "/health", "/assets/", "/static/")
if any(path.startswith(p) for p in skip_paths) or path == "/favicon.ico":
    return await call_next(request)      # ← 永远走这里
```

`skip_paths` 里含 `"/"`，而**任何**路径都以 `/` 开头 → `any(...)` 恒为 `True` → 中间件整体空转。


**修法**：把 `"/"` 从 tuple 里删掉，改成 `path == "/"` 单独判断；静态资源按前缀判断要放在最后，且必须排除 `/api/` 前缀。

## 四、P2 — 健壮性与一致性

**时区混用（影响"今日目标"准确性）**
- `spider.py` `_mark_song_crawled` / `_get_priority_targets` / `_get_comment_targets` 用 `datetime.now()`
- `app.py:664,672` `api_crawler_stats` 用 `datetime.now()` 算 24h 与"今日入库"，但 `Song.created_at` 存的是 CST
- 项目已有 `cst_time.now_cst()/today_cst()` 且注释明确"全局禁止 datetime.now() 写入 DB"，但至少 6 处违反 → 服务器时区非东八区时"今日进度"算错

**DB 路径不确定**
- `db.py:get_db_url()` 返回 `sqlite:///data/netease163.db`（相对进程 CWD）
- `constants.py:DEFAULT_DB_URL` 指向 `PROJECT_ROOT/netease163/data/netease163.db`
- 两者不一致 → 换个启动目录就换一个库，数据"凭空消失"

**性能 / N+1**
- `app.py:249-261` `get_comment` 一次性把该歌**全部** ai_* 行读进内存（无 limit），大歌数千行 × 7 字段
- `app.py:702-709` `songs/latest` 每首歌单发一次 count 查询
- `app.py:196-210` `comment/by-name` 每个候选单发一次 CommentSpider 请求（N 次串行）
- `app.py:773-836` `get_candidates` 对每个候选串行 `SongSpider.fetch` + `CommentSpider.fetch`，且**在 GET 搜索接口里写库**

**安全（中低危）**
- `app.py:525` `content.like(f"%{keyword}%")` — 用户输入 `%` / `_` 未转义，可构造全表扫描（参数化查询，非注入，但可被用来打满 CPU）
- `app.py:893` `is_sensitive_keyword` 双向子串匹配（`keyword in sensitive`），单个汉字（"人"、"色"）会被误判为敏感词

**状态管理**
- `app.py:942` 删除关键词只改内存 `kw_module._pool_instance._pool`，不落库；而新增会写 `SearchLog` → 服务重启后删掉的关键词全部复活
- `app.py:614` `/random/crawl/now` 用 **GET** 触发耗时数分钟的状态变更操作，且同步阻塞

**数据质量**
- `toplist.py` 返回的 track 没有 `album` / `pic_url` / `duration_ms`，且 `artists` 是字符串数组；而 `SongSpider` 返回 `[{id,name}]` → 榜单来源的歌入库后封面空白、专辑名为空，两种结构混在同一列里
- `spider.py:115` `_get_priority_targets` 注释说"按 comment_total 选 7 天前的歌"，实际 `order_by(desc(Song.id))` — 网易云 song id 不等于入库时间，重爬优先级基本是随机
- `spider.py:55,510` `ROUND_FULL_CRAWL_SONGS=3` × `MAX_PAGES_PER_RUN=20` × 每页 8-25s ≈ 单轮最长 25 分钟，而 cron 是 `*/20` → 轮次持续重叠，靠 flock 静默跳过，实际吞吐远低于设计值

**前端**
- 死代码：`jumpToComment`(988)、`navigateToComment`(1419)、`navigateToSong`(1427) 定义后无任何调用
- 重复定义：`loadLyricById`（888 / 995）、`loadCommentById`（916 / 1008）各定义两次，后者覆盖前者
- `escapeHtml`(462) 未转义反斜杠 → 歌名以 `\` 结尾时内联 `onclick` 的 JS 字符串被转义破坏，语法错误

**测试（已失效，必然挂）**
- `test_api.py:81-90` 测 `/api/v1/my/recommend`、`/api/v1/my/fm` — 这两个路由早已删除 → 404 ≠ 401
- `test_api.py:99-104` `test_login_phone_wrong_creds` 仍用 URL query 传参，接口已改 Pydantic Body → 422 ≠ 200
- `test_basic.py:16-17` 重复导入 `SongModel/CommentModel`（无害但冗余）

**文档漂移**
- `README.md:83` 称 11 张表，实际 10 张；且列出的 `playlist_songs`、`crawl_priority`、`keywords`、`crawl_log` 四张表**都不存在**（实际叫 `crawl_logs`）
